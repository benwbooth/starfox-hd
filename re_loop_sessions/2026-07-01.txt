The cockpit color fix is underway (comparing the game render against the mesh viewer, which renders the Arwing correctly, and the actual `NIGHT.COL` palette values — top suspects are my GSU intensity-curve scale factor and a possible depth-bank flip at title-screen distance).

**On 16-bit precision and smoothness — here's the honest architectural picture:**

The choppiness you feel is mostly *not* 16-bit precision. It's three separable things:

1. **20Hz game logic.** The original runs game logic at ~15–20fps (Super FX frame time), and our port replicates that with a fixed 20Hz tick. Everything gameplay-visible moves in 50ms steps.
2. **Render interpolation defects.** We already render at vsync/uncapped and interpolate between ticks — but the interpolator pairs draw-list entries *by index*, so when spawn order shifts between ticks, objects get interpolated against the wrong partner. That's very likely your "ship bounces around" bug, and the motion agent is on it. Fixing pairing (stable entity IDs) makes the existing interpolation actually smooth.
3. **16-bit sim quantization** is real but third-order: positions snap to integer SNES units, angles to 256ths. You only notice it after 1 and 2 are fixed.

**The plan that gets you smoothness without sacrificing accuracy:**
- **C oracle: don't touch the math.** Its 16-bit quirks *are* the fidelity reference — changing them destroys its value for differential testing.
- **Rust port: two modes.** *Fidelity mode* reproduces the 16-bit math exactly (validated tick-for-tick against the oracle — this is how we prove the port is right). *Enhanced mode* — the actual "HD" deliverable — then widens the sim to i32/f64, raises the logic tick to 60/120Hz with time-scaled constants (timers, velocities, spawn cadences all expressed per-second instead of per-tick), and keys interpolation on entity identity. Because enhanced mode diffs against fidelity mode at matched timestamps, we can verify the enhancements don't change *behavior*, only granularity.

That ordering means precision work happens once, in Rust, instead of twice.

**On "tons of other weird bugs":** agreed, and I've queued the fix for the workflow itself — after this fix wave lands and we commit the checkpoint, I'll add an `SF_START_MAP` hook so tests can jump straight into any level, then run a systematic sweep: autoplay + frame-dump every live map, catalog every deviation against reference footage, and triage into a fix queue.
